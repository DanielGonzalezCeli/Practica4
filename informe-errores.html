Errores encontrados

1No encontraba la carpeta productos ni producto.model.tsConfusión

Síntoma
Al llegar al Paso 2 busqué src/productos/producto.model.ts y no existía.
Causa
nest new solo genera app.controller, app.module, app.service y main. La guía pide crear la carpeta y los archivos; no vienen en el proyecto.
Solución
Crear src/productos/ con producto.model.ts y productos.resolver.ts usando el código de la guía.

2El app.module.ts de la guía importa @nestjs/observeError

Síntoma
Tras copiar el app.module.ts del Paso 3, el import import { createObserveModule } from '@nestjs/observe' apunta a un paquete que no está en package.json ni en node_modules.
Causa
La guía asume que nest new genera un proyecto con ObserveModule y un main.ts que usa ObserveInstrument. Mi proyecto se generó sin eso: main.ts es el clásico de tres líneas y tampoco tiene "type": "module" en package.json.
Solución
No instalar el paquete (habría quedado configurado con las claves de relleno YOUR_APP_KEY). Se eliminaron de app.module.ts el import, la línea createObserveModule() y el bloque ObserveModule.forRoot({...}). Lo mismo al repetir el archivo en el Paso 6. 
@Module({
  imports: [
    GraphQLModule.forRoot<ApolloDriverConfig>({
      driver: ApolloDriver,
      autoSchemaFile: join(process.cwd(), 'schema.gql'),
    }),
    HttpModule.register({}),
  ],
  controllers: [AppController],
  providers: [AppService, ProductosResolver],
})
export class AppModule {}
Los imports con .js funcionan igual sin "type": "module", porque tsconfig.json usa module: nodenext.

3El puerto 3000 respondía otra aplicaciónError

Síntoma
Las consultas a http://localhost:3000/graphql devolvían un 404 que no era de este proyecto: 
{"title":"Recurso no encontrado","status":404,"detail":"Cannot POST /graphql"}
Causa
Otro proyecto de Node ya estaba escuchando en el puerto 3000 de mi máquina.
Solución
main.ts lee process.env.PORT, así que se arrancó en otro puerto (PORT=3456) y se probó en http://localhost:3456/graphql. La alternativa es detener la otra aplicación.

4TS5011 al ejecutar npm testError

Síntoma
Fallaba incluso la prueba que trae el proyecto recién generado: 
error TS5011: The common source directory of 'tsconfig.json' is './src'.
The 'rootDir' setting must be explicitly set to this or another path...
Causa
TypeScript 6 exige un rootDir explícito. tsconfig.build.json lo define para compilar, pero ts-jest usa tsconfig.json, que no lo tiene.
Solución
Se añadió tsconfig.spec.json (extiende tsconfig.json con "rootDir": ".") y se indicó a ts-jest que lo use en jest.config.ts y test/jest-e2e.json.

5Jest no podía cargar los paquetes de NestJS 12Error

Síntoma
Must use import to load ES Module: ...\node_modules\@nestjs\testing\index.js
Causa
Los paquetes de NestJS 12 se publican como módulos ES ("type": "module"). Jest solo puede cargarlos desde pruebas CommonJS si Node se ejecuta con soporte de módulos en vm.
Solución
Los scripts de prueba de package.json ejecutan Jest con esa opción: 
"test": "node --experimental-vm-modules node_modules/jest/bin/jest.js"
Además se añadió un moduleNameMapper para que los imports relativos terminados en .js se resuelvan a los archivos .ts durante las pruebas.

6productoPorId(id: 2) responde INTERNAL_SERVER_ERROREsperado

Síntoma
{"errors":[{"message":"Request failed with status code 404",
  "path":["productoPorId"],"extensions":{"code":"INTERNAL_SERVER_ERROR"}}]}
Causa
La API real solo tiene los ids 1, 3 y 4. Para el id 2 responde 404 Producto 2 no existe; Axios lo convierte en excepción y Apollo lo muestra como error interno.
Solución
Ninguna: es el comportamiento que describe la guía. Con los datos en memoria del Paso 4 la misma consulta devolvía null.

Otras diferencias con la guía

  • Versiones de mi máquina: Node v24.14.0 y npm 11.9.0 (la guía se probó con v24.19.0 y 11.17.0). npm install muestra avisos EBADENGINE porque @angular-devkit pide Node ^24.15.0; son solo avisos y todo funcionó.
  • package.json guarda las dependencias con ^ (por ejemplo ^14.0.3); las versiones exactas instaladas quedan fijadas en package-lock.json.

Pruebas y GitHub Actions

El flujo .github/workflows/ci.yml se ejecuta en cada push a main con Node 24 y corre: npm ci, npm run lint, npm run build, npm test y npm run test:e2e.

  • Unitarias (5): ProductosResolver con HttpService simulado: productos, productoPorId y productosBaratos con 50 y 100; más la prueba de AppController.
  • End-to-end (5): levantan la aplicación completa y envían consultas GraphQL reales a /graphql.
  • En las pruebas la API de Render se reemplaza por un doble, para que el CI no dependa de internet ni de que el servicio esté despierto.

Comparación con REST

Para "todos los productos, solo nombres, más el detalle de uno" con REST hacen falta 2 llamadas (GET /api/v1/productos y GET /api/v1/productos/4) y la primera trae además id y precio. Con GraphQL es una sola petición que pide exactamente esos campos. Entre el Paso 4 y el Paso 6 la forma de las consultas no cambió: solo cambió el origen de los datos, del arreglo catalogo en memoria a HttpService.
